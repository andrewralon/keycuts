# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What keycuts is

keycuts creates **generated `.bat` files** that let you open anything on your computer by nickname. The `.bat` is written into a folder on the system `PATH`, so Windows Run (`Win+R`) resolves a bare name (`npp`, `gmail`, `db`). The generated script is the whole product: there is no database and no config file holding the shortcut list. The "list" is whatever `.bat` files are in the output folder (default `%USERPROFILE%\Shortcuts`, chosen in the installer, stored in `HKCU\Software\TeamRalon\keycuts`).

Entry points for creating one: the WPF app (drag/paste/browse a destination, name it, Enter), the Explorer right-click verb (launches the GUI with the destination as `args[0]`, handled in `keycuts.GUI/App.xaml.cs`), the CLI, or referencing `keycuts.Common`.

## Commands

.NET SDK 10, Windows only (Common and CLI target `net10.0-windows`; GUI and Tests target `net10.0-windows10.0.19041.0`). `global.json` pins the SDK to the 10.0.2xx feature band, version 10.0.203 or a newer 2xx patch (`latestPatch`), and CI installs the newest 2xx patch. A machine without a 2xx SDK fails with an SDK-resolution error; install one, or move the band deliberately in `global.json`. Run from the repo root:

- Build: `dotnet build keycuts.sln`
- Test: `dotnet test keycuts.sln` (xUnit, project `keycuts.Tests`)
- Single test: `dotnet test keycuts.Tests --filter "FullyQualifiedName~KeycutCreatorTests.SomeTest"`
- On macOS/Linux: `dotnet build keycuts.sln -p:EnableWindowsTargeting=true` and `EnableWindowsTargeting=true dotnet format ...` work, but the tests can't run there (the test host needs the WPF runtime), so CI is the test run.
- Format check: `dotnet format keycuts.sln --verify-no-changes --severity error` (keep it clean; without `--severity error` it also reports baseline warnings and exits non-zero)
- Installer: `pwsh -File tools/Build-Installer.ps1 [-Version x.y.z] [-Runtime win-x64|win-arm64]` (the version defaults to `Directory.Build.props`, the runtime to `win-x64`) publishes self-contained to `artifacts/publish/<runtime>` and builds `artifacts/installer/<runtime>/keycuts-setup-<arch>.msi`. Each runtime has its own folders, so building one keeps the other; the WiX build is `--no-incremental` because both share `installer/obj`. Both MSIs share the upgrade code and `AllowSameVersionUpgrades`, so installing one replaces the other. Needs only the .NET SDK; WiX restores from NuGet. `installer/` is deliberately not in `keycuts.sln`, so normal builds stay fast. WiX builds into `en-US/` because of `Package.en-us.wxl`; the script moves the output back up.

Gotchas:
- The build has **0 warnings**. Each project's `AssemblyInfo.cs` declares `SupportedOSPlatform("windows")` by hand; `Directory.Build.props` lets the SDK generate only the version attributes for projects that have one. A new project with its own `AssemblyInfo.cs` needs the same line or CA1416 comes back. Count with `--no-incremental`; an incremental build skips compilation and reports 0.
- If `keycuts.GUI.exe` is running, the build fails with MSB3021/MSB3027 (file locked). That is not a code error; stop the process (the user has approved force-closing it). Close any instance you launch.
- Package versions live only in `Directory.Packages.props` (Central Package Management); `PackageReference` items carry no `Version`. `nuget.config` restores from nuget.org only. There are no lockfiles, because the installer's `-r win-x64`/`-r win-arm64` publishes would rewrite them.
- Tests must use temp folders and must never touch the real output folder or the registry. Use `KeycutCreator`/`KeycutRepository` with an explicit `OutputFolder`, an explicit `Overwrite`, and a fake `IPathUpdater`; a null `Overwrite` falls through to `Runner.GetForceOverwrite()`, which reads `HKCU`. Use `ContextMenuRegistrar` with a fake `IClassesStore`, and `SettingsViewModel` with a fake `ISettingsStore`. Test classes that host WPF windows or views go in `[Collection(WpfCollection.Name)]`: they share the one `Application` per AppDomain and fail if two create it in parallel.
- Debug builds honor the `KEYCUTS_OUTPUT_FOLDER` env var (`DebugOverrides`) to redirect the output folder without touching registry/PATH; it is inert in Release. `tools/New-SampleKeycuts.ps1` generates fixture folders (refuses the real output folder).
- CI (`.github/workflows/ci.yml`) runs on PRs into `develop`/`main` and pushes to `develop`. Job `build` (Windows) builds and tests, and job `format` checks formatting on Linux beside it; both are required checks on `develop` and `main`. Each run's summary shows the version, SDK and runner image, the test results (`GitHubActionsTestLogger`, which also annotates failed tests), the diff of any changed characterization snapshot, and, on failure, the formatting issues by line. A failed run uploads a `test-results` artifact (TRX plus any `.received.txt` snapshots). PRs into `main` also run job `installer` beside `build` (required on `main`): it builds both MSIs (x64 and arm64), including WiX ICE validation, uploads them together as `keycuts-setup`, and puts the release preview with each one's size and SHA256 in the summary. Actions are pinned to commit SHAs; Dependabot (`.github/dependabot.yml`) bumps them and the NuGet packages monthly.

## Versioning and releases

`<Version>` in `Directory.Build.props` is the only version. It stamps every exe (`Runner.Version`, which goes into each `.bat` header) and the MSI. Every push to `main` runs `.github/workflows/release.yml`: if tag `v<Version>` doesn't exist yet it tests, builds both MSIs, and publishes a GitHub release with `keycuts-setup-x64.msi`, `keycuts-setup-arm64.msi`, `keycuts-portable-win-x64.zip`, `keycuts-portable-win-arm64.zip` and `SHA256SUMS.txt`; otherwise it does nothing. To release, raise the version on `develop` (three parts; MSI upgrades ignore a fourth), then merge `develop` into `main`. Don't create release tags by hand.

## Architecture

Four SDK-style projects in `keycuts.sln` (the old `keycuts.Batmanager` app was retired, and its manager is now a view inside the GUI; the `keypaste` project became `keycuts paste`, #97):

- `keycuts.Common`: all domain logic, no UI. Resolves `.lnk` files through late-bound `WScript.Shell` COM (`Type.GetTypeFromProgID`), so there is no COM reference in the csproj.
- `keycuts.GUI`: WPF, single window with two views (Creator, Manager) driven by `ViewModels/` (`ShellViewModel` switches views). Side-effects go through `IKeycutActions` so view models are testable. `Themes/` holds tokens, light/dark/high-contrast dictionaries and `ThemeManager`; `Controls/` has `Icon`, `TypeBadge`, `MenuButton`, `SortHeaderButton`. Settings is a modal dialog (`SettingsWindow`) over `SettingsViewModel`; `RunnerSettingsStore` is its seam over `Settings`/`Runner`, and its toggles use the `ToggleSwitch` style.
- `keycuts.CLI`: assembly is named **`keycuts.exe`**, not `keycuts.CLI.exe`. Uses CommandLineParser 2.9.1 with two verbs: `create` (`Options`, the default verb, so the original `keycuts -d … -s …` needs no verb name) calls `Runner` directly and has no description option; `paste <name>` (`PasteOptions`, #97, formerly the `keypaste` project) runs `KeycutPaste.Run` in Common and sets the clipboard through Win32 (`WindowsClipboard`), so nothing in the solution uses WinForms. PATH gets only the install folder's `bin\` (`BINFOLDER` in `installer/Package.wxs`, harvested separately from the rest), never the install folder itself, which would put the self-contained runtime's DLLs and `createdump.exe` on PATH; this is VS Code's `bin\code.cmd` pattern. It holds two shims from `keycuts.CLI/shims/` (copied to `bin\` by a `Link`): `keycuts.cmd` (`@"%~dp0..\keycuts.exe" %*`) and `keypaste.cmd` (`... paste %*`), so `keypaste <name>` still works. A bare `keycuts` (no arguments) starts `keycuts.GUI.exe` from the same folder (`GuiLauncher`), so Win+R opens the app; any argument keeps it the CLI, and a CLI-only copy with no GUI beside it prints help as before. `Usage` builds the help: `-h`/`--help` and `--version` print to stdout and exit 0, and a parse error or a create missing `-d`/`-s` prints a short reason to stderr and exits `BadArguments` (1). `keycuts.exe` can't move into `bin\` itself: a self-contained apphost needs its runtime in its own folder. `.gitattributes` keeps the shims CRLF.
- `keycuts.Tests`: references Common and GUI; covers creation, repository, resolver, view models, accessibility, sample data.

### Two layers of creation code in `keycuts.Common`

The newer code wraps the legacy code rather than replacing it. Every create ends in the same place: `KeycutCreator` (GUI) validates, then calls `Runner.Run`, as the CLI does directly; `Runner.Run` builds a `Shortcut` and calls `CreateShortcutFile`. Reads also share one parser: `KeycutRepository.TryParse` wraps `ShortcutFile`. So a change to the emitter or parser affects every entry point.

- **Legacy**: `Runner.Run` / `Runner.CreateShortcutFile` (the `.bat` emitter, returns `ExitCode`), `Shortcut` (classifies a destination into `ShortcutType`, resolves `.lnk`/`.url`), `ShortcutFile` (regex parser that reads a `.bat` back), `RegistryStuff` (`HKCU` settings; reads never write).
- **Newer, structured**: `DestinationResolver` (validates and classifies a destination, returns `DestinationResult`/`DestinationError`), `KeycutCreator` (returns `CreateResult` with a `CreateOutcome`, async, takes `CreateOptions` including an injectable `IPathUpdater`), `KeycutRepository` (loads/deletes `.bat` files in one folder, background destination checks), `Keycut`/`KeycutKind` (the manager's model). Validation differs by caller: the GUI gets `DestinationResolver` and name checks first, the CLI doesn't. The legacy `GetShortcutTypeFromDestination` still runs on every create (the `Shortcut` constructor) and in `MainFormLogic`.

### The `.bat` format

`Runner.CreateShortcutFile` writes a header (`REM keycuts <version>`) plus `REM <shortcut>`, `<type>`, `<destination>`, and `<description>` comment lines, then the launch command and `EXIT`. `ShortcutFile` reads the description, type and destination from those comments. Type and destination are used only when both are present and valid (`TryParseRemTypeAndDestination`), and then they win even if the launch command disagrees; `Command` and `OpenWithApp` always come from the launch line. Otherwise (the 0.1.x format has no such lines) type and destination are recovered by regex-parsing the launch command (lines containing `explorer.exe` or starting with `START`), tried in order: the emitter's `cmd /C` command, CLSID, folder, hosts, the 0.1.x `START "" /D "<folder>" "<file>"` form (joined into one path), file, command, URL. No other pattern splices quoted parts together, so a File destination may hold a program plus its quoted arguments (`app.exe" "arg`), which re-emits the same line. A URL's launch line is escaped for cmd (`Shortcut.SanitizeBatEscapeCharacters`: every `%` doubled, `^` before every `^ & | < >` outside double quotes, where cmd reads a `^` literally); the parser reads a launch line as written and doesn't unescape it (see the gameplan's Decisions), and File/Folder paths aren't escaped at all, which is what lets a destination saved with environment variables (`%USERPROFILE%\Desktop`, #31) expand when the `.bat` runs. That substitution (`PathVariables.Substitute`, longest folder match) happens in `Runner.Run` **after** the destination is classified, because the legacy classifier would read `%USERPROFILE%\...` as a relative path; it runs only when `KeycutArgs.UseEnvironmentVariables` is set (the GUI: the setting flipped by Shift; the CLI: the setting). Tests pass their own `PathVariables`; `PathVariables.GetDefault()` reads the environment, the registry and the disk, and tests use its overload that takes those as functions. Files without a description line show an empty description. A corpus of real `.bat` files, including a second legacy header schema (`keycuts 0.1.1.5`), lives in `tests/corpus/legacy/` (see its README).

## Surprises and known landmines

- `ShortcutType.Command` is still never produced by a create: `Shortcut.GetShortcutTypeFromDestination` never returns it. The emitter writes `START "" /B cmd /C "<command>"` for it, which the regex fallback reads back as Command (`IsEmittedCommand`, an exact inverse tried before the unanchored Explorer patterns). A `START "" /B "<anything>"` line still reads as File, because File is tried before Command.
- The emitter's launch line (`Runner.BuildCommand`) is a `switch` with no discard arm, so adding a `ShortcutType` without a case is a build error (CS8509). `Unknown` throws.
- **PATH management** (`UserPathUpdater`, reached from `Runner.Run` and `Runner.ChangeOutputFolder` through `IPathUpdater`) edits the user `PATH` in `HKCU\Environment` directly, because `Environment.SetEnvironmentVariable` would expand `%VARS%` and rewrite the value as `REG_SZ`. It is a no-op when old and new folders match, so the installer is what first puts the output folder on `PATH`. GUI creates never change `PATH`: `KeycutCreator` uses a fixed-folder `Runner`, which passes the same folder as both. Old entries on the machine `PATH` can't be removed without elevation and are left alone.
- `Shortcut.GetShortcutTypeFromDestination` returns `Unknown` for a missing or unreadable path, which `Runner.Run` reports as `ExitCode.NotStarted`. `DestinationResolver` is still the validator that gives a reason.
- The regex fallback's CLSID pattern starts with `[shell:]?`, a character class, not the word `shell:`. So a launch line for a `shell:::{...}` destination (which `DestinationResolver` accepts) doesn't match it and is read back as a Folder. Only files without valid REM type and destination lines hit this. (File and Folder destinations used to keep their surrounding quotes and CLSID keys used to lose their `::`; `ShortcutFile.Unquote` removes exactly one pair of quotes, the inverse of the emitter's wrapping, so don't add another trim on top.)
- **Nothing needs elevation.** Context-menu verbs live in `HKCU\Software\Classes` (`ContextMenuRegistrar`, handler resolved from `AppContext.BaseDirectory`). Never write through `Registry.ClassesRoot`: it resolves to `HKLM` for these keys, and that write crashed the Settings window. The MSI writes the same keys in `installer/Package.wxs`, and a test compares the two lists.
- The Settings toggle shows whether the verbs exist, not the `RightClickContextMenu` value. That value only records the user's choice, so an MSI upgrade doesn't re-add a menu they turned off.
- The first-run welcome panel (`WelcomeViewModel`, on `CreatorViewModel.Welcome`) decides once, from the shell's first keycut count: it shows when `WelcomeDismissed` is unset in `HKCU` (the first run, upgrades included) or the folder is empty, and Settings → Show welcome calls `ShellViewModel.ShowWelcome`. The self-keycut's default name is `kc`, not `keycuts`, because the CLI's `keycuts.cmd` is on PATH too and one would shadow the other. It is wired up only in `App.xaml.cs`; tests pass fakes for the HKCU read/write and the create call, and a `CreatorViewModel` without one shows no panel. The self-keycut points at `Environment.ProcessPath`, so a Debug run creates one to the Debug exe. GUI creates never change PATH, so after the self-keycut the panel checks `UserPathUpdater.IsOnPath` (registry user and machine PATH, as Win+R sees them) and offers **Add to PATH** if needed; with the Debug `KEYCUTS_OUTPUT_FOLDER` override it skips that check, so it never writes PATH.
- Windows 11 shows these classic verbs under "Show more options". The top-level menu needs a packaged `IExplorerCommand` handler.
- `OUTPUTFOLDER` in `installer/Package.wxs` is a directory so the stock `InstallDirDlg` can edit it, which means Windows Installer stores it with a trailing backslash; `RegistryStuff.GetOutputFolder` trims that. The dialog only shows on a first install. Windows Installer has no standard directory for the profile, so the default comes from `[%USERPROFILE]`; a test compares it to `Runner.DefaultOutputFolder`.
- Manager rows take no keyboard focus. `ManagerView_PreviewKeyDown` handles Up, Down, Enter and F2 for the whole view, so typing in the search box keeps working, and `ManagerViewModel.SelectedRow` holds the selection. While a row is being renamed (`ManagerViewModel.IsRenaming`) that handler steps aside, the name box handles Enter, Escape and the arrows itself, and `LoadAsync` is skipped so a reload can't throw away the typed name.
- A keycut named after a command on PATH (`CommandNames`: `keycuts`, `keypaste`, matching the shims; a test compares them) clashes with it, since Windows takes whichever comes first on PATH. `KeycutCreator.IsValidName` refuses those names (GUI create, rename, welcome; the CLI doesn't validate names), and `App.xaml.cs` calls `KeycutRepository.MoveAsideCommandNames` before the first load, which renames an existing one to `<name>_previous` (then `_previous2`...) the way `RenameAsync` does and shows `CommandNameNotice` once. A locked file is skipped and retried next start.
- Renaming a keycut (`KeycutRepository.RenameAsync`) moves the file and rewrites only its `REM <shortcut>` line; it never re-emits the file, so a hand-edited launch line survives. It refuses a taken name (a change of case only is allowed) and leaves a file that isn't valid UTF-8 byte for byte.
- The hosts file is classified by one check, `Shortcut.IsHostsFile`, used by both the legacy classifier and `DestinationResolver`. It compares the full path with this machine's System32 (`Environment.SystemDirectory`, so Windows on another drive works) and the usual `C:` path. The legacy classifier used to compare with an unexpanded `%windir%` path, which could never match.

## Conventions

`#region` blocks, `var` everywhere, `out` parameters as the legacy return idiom. The library doesn't log: don't add `Console.WriteLine` to `keycuts.Common` (the CLI's output is its own; `Runner`'s "Shortcut created" line is the one exception, and `keycuts paste` sends library output to stderr). `.editorconfig` enforces Allman braces, 4-space C# / 2-space XAML and csproj. `keycuts.GUI` has `Nullable` enabled; `Common` does not. Match the surrounding style.

## Sequencing rule

The parser has thin test coverage and the plan changes both the file format and the platform underneath it. **Never move two variables in one commit.** Current behavior (bugs included) is pinned by `keycuts.Tests/Characterization/`. `CharacterizationRenderer` renders the parse of every corpus file, the emitter output for each type, and a `Parse(Emit(Parse(f)))` round trip as text, twice: once reading the whole emitted file (`RoundTrip`), and once without its REM `<type>` and `<destination>` lines (`LaunchLineRoundTrip`, the one that shows whether the emitted command is right); `CharacterizationTests` compares each rendering with `Snapshots/*.verified.txt`. When one differs, the test writes a `.received.txt` next to it (gitignored; in CI, download it from the failed run's `test-results` artifact). If the change is intended, copy it over the `.verified.txt` in the same commit, so the behavior change is a reviewable diff. Known wrong answers are annotated in `ParserNotes` and the emitter cases. Pure entry points for this: `Runner.BuildShortcutLines`, `new ShortcutFile(path, lines)` and `Shortcut.FromParts`.
