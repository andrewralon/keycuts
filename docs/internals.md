# Internals

Behavior that spans several files. Read the section before changing that area. Per-method detail lives in code comments.

## Window and shell

- One window, three screens (`ShellMode`). The top row is `RailView`: a `RailTabControl` (a `TabControl` showing only headers, so screen readers get a real tab list) plus our own caption buttons. `WindowChrome` makes the bar draggable; tabs and buttons are `IsHitTestVisibleInChrome`. No tab keyboard shortcuts.
- Ctrl+1, Ctrl+2 and Ctrl+3 pick the tabs (`MainWindow.Main_KeyDown`, on the bubbling `KeyDown`, so a control that wants the key keeps it); not while `AreTabsEnabled` is off.
- Never maximized: `NoMaximizeHook` strips `WS_MAXIMIZEBOX`, refuses `SC_MAXIMIZE` and undoes `WindowState.Maximized`. The Manager and Settings keep resize edges and side snapping. Resize border is 0 on the Creator and `WindowLayout.GetFrameThickness` on the Manager and Settings.
- A selected tab's shadow is its own shape (`Shadow` in `RailTabItem`). A shared effect set from a trigger can't be frozen and fails across test threads.
- Two sizes (`MainWindow.ApplyMode`). Small, the Creator: MainWidth, `SizeToContent.Height`, no resize border. Large, the Manager and Settings: one shared, resizable size (`largeSize`, 768 × 470, just wide enough for Runs, until the window first leaves it), clamped to the work area. Switching between the two large screens touches nothing, so resizing either resizes both; Settings never grows the window and scrolls instead. The window keeps its top-left corner both ways: a Manager moved elsewhere leaves the Creator there too.
- Settings is always two columns, down to the window's minimum 720 × 470, where it still fits without scrolling (the owner's pick, 2026-11-17).
- The shell numbers its reloads; only the latest may set the count or reach the welcome panel. A count-only reload cancels a running Manager load (`ManagerViewModel.CancelLoad`).
- Tests: tab bar names are in `RailView`'s name scope (not `Window.FindName`); a `TabItem`'s automation peer comes from the tab list's peer.

## Settings

- `SettingsView` over `SettingsViewModel`, created fresh by the shell's `settingsFactory` (wired in `App.xaml.cs`; a shell without one can't open Settings).
- Every change is stored at once. `ISettingsStore.SaveOptions` stores everything but the folder; `SaveOutputFolder` stores the folder alone and returns `FolderSaveResult`. A partial failure (PATH, menu) shows as `SaveError`. A folder that wasn't stored stays as an uncommitted edit.
- Folder commits on Enter, focus loss or the folder picker (`CommitOutputFolder`). Escape in the box reverts an uncommitted edit (`RevertOutputFolder`); otherwise Escape closes the icon picker, else returns to the Creator (`ShellViewModel.HandleEscape`).
- Events `Stored`, `OutputFolderChanged`, `ShowWelcomeRequested`, `UpdateChecked` keep the shell in step.
- Restore defaults (`Settings.Defaults()`) confirms in `ConfirmWindow`, never touches the folder or PATH.
- The right-click toggle shows whether the verbs exist, not the stored `RightClickContextMenu` value (which only records the choice so an MSI upgrade doesn't re-add a removed menu).
- `ShowVersionRow = false` hides the version row in screenshots. The row reads "Version · 2.1.0 (abc1234)": the number, then `BuildInfo.Commit` (`Common/BuildInfo.cs`), the first seven hex characters after the `+` the SDK adds to `AssemblyInformationalVersion` when the build has git information (every build from a checkout, release builds included; no `SourceRevisionId` is set). A source archive has none and shows the number alone. The three-part `<Version>`, the MSI, the update check and `keycuts --version` (`Usage.GetVersion` strips the `+…`) never see it. `SettingsViewModel.Commit` is settable so tests don't depend on the checkout.

## Creator and footer

- `FooterView` is shared by the screens and is collapsed (its `Bar`, bound to `UpdateNotice.IsVisible`) unless a newer version is out; it holds only the update line. The Manager's status and Undo are `ManagerStatusView` in the search row, collapsed while `StatusMessage` is empty and `CanUndoDelete` is off. The count is `ManagerViewModel.CountText` in a pill beside the search box ("of" only while `SearchText` isn't blank, since the shell can set the total before the rows reload), announced via `LiveRegion.Announce` when it changes.
- The Target box shows `TargetText` (the `%VAR%` form when Shift is held or the setting is on) only while it isn't focused (`IsTargetEditing`). `Target` always holds the real path.
- The description box is always shown (2026-11-17; the old `ShowDescription` value in HKCU is no longer read).
- Saving/Created is `NameStatusText`, under the name box in the Creator (beside the Name label in the Manager's create row); the helper line under Name takes no room unless it has a warning. Fields stay filled after a create; Created clears after `SuccessDuration` (3 s).
- `HelperText` controls announce their own changes; don't also call `LiveRegion.Announce`.
- **Two forms.** The Creator and the Manager's create row are each a `CreatorViewModel` (`ShellViewModel.Forms`); the row's is `ManagerViewModel.CreateRow`, with `DescriptionAlwaysShown` and `ClearsAfterCreate`. What the app reads once (the environment-variables setting, the path variables) goes to both. Their views attach a `CreatorInput` (drop, paste, Ctrl+V, Browse, resolve while typing, the name check, Shift, the confirm dialog), which lets go of the view model while the view is unloaded, so a hidden view never answers a Browse. Shared styles are in `Views/CreatorForm.xaml`; the drop area's triggers find an element named `DropArea` in the view.
- **The Manager's create row.** `CreateRowView`, in a `ContentControl` with an implicit template, so a Manager without a `CreateRow` (tests) builds none. `TargetEnterCreates`: Enter in its target resolves, then creates if the name is filled, else moves to the name. `ManagerView_PreviewKeyDown` ignores keys from inside the row except Ctrl+F. A create there reloads the table (the shell listens to `KeycutCreated`). The Manager opens with the focus in the search box, not the row.

## Welcome panel

- `WelcomeViewModel` on `CreatorViewModel.Welcome`, wired only in `App.xaml.cs`. Shows when `WelcomeDismissed` is unset or the folder is empty, decided once from the first count.

## Manager

- **Keys.** Rows take no focus; `ManagerView_PreviewKeyDown` handles Up/Down, Page Up/Down, Home/End, Enter, F2, Shift+F2, Delete, Ctrl+C/E/F/Z, Ctrl+Shift+E/O. Delete/Home/End stay with the search box while it has text, Ctrl+C while text is selected. Shift+F10 and the Menu key open the selected row's menu under the row, and stay with the search box while it has text too: Avalonia raises `ContextRequested` without a position for them, which `ManagerView_ContextRequested` answers. Ctrl+E on a non-editable row explains in the status line (in the search row). Enter on a button (the footer's Download) is left to the button.
- **Editing in place.** A click on the name/description of the already-selected row starts rename or description edit (not the click that dismisses a menu, nor within 250 ms of one). Only one edit at a time (`IsEditing`); reloads wait; clicking away saves.
  - `RenameAsync` moves the file and rewrites only `REM <shortcut>`. Refuses taken names (case-only change allowed).
  - `SetDescriptionAsync` rewrites only `REM <description>` (inserting it before the launch line if missing), preserves line breaks, BOM and streams (temp file + `File.Replace`), refuses non-UTF-8 (`NotEditable`) or a changed file (`Changed`), and doesn't touch an unchanged file.
- **Edit form** (`EditWindow`/`EditKeycutViewModel`, opened via `ManagerViewModel.ShowEditForm`). Re-emits the whole file, so `CanEditInForm` accepts only files the emitter writes identically (ignoring header version, `<destination>` tag, `REM <shortcut>` path, missing description). File is read as strict UTF-8 from bytes, not `File.ReadAllText`. `UpdateAsync` refuses a changed file, writes temp + `File.Replace`, renames with `File.Move` first and puts the name back if the swap fails. `KeycutEditTests` pins every corpus file.
- **Delete and Undo.** `CreateDefault()` recycles; `new KeycutRepository(folder)` deletes permanently. Undo is one level, lives as long as the "Deleted" message (8 s), and restores the kept bytes via temp file + no-overwrite `File.Move`. A failed restore keeps the Undo. Delete and restore exclude each other. Permissions and alternate streams aren't restored (accepted). Drives without a bin say so.
- **Row menu.** No `...` column: each `DataGridRow` gets its own menu, built from the `RowMenu` template in `Table_LoadingRow` (a style setter would share one instance), so its bindings follow the row through recycling. A right-click opens it at the pointer and selects the row; the keyboard path places it with `MenuPlacement.UnderLeftEdge` and `RowMenu_Closed` puts it back to `Pointer`. After a non-destructive item or Escape, the focus goes to the search box.
- **Order.** After an edit or Undo, `SortLikeTheFolder` keeps `allRows` in folder order so the next reload doesn't rebuild rows under the focus.
- **Column widths.** Name, Description, Target are draggable star columns; Type, Modified, Runs, Last run are fixed. Avalonia.Controls.DataGrid (MIT) with the Manager's own row, cell and header themes. A row is `RowHeight` plus its 1px divider, as in WPF: 36 draws 37 px rows. The headers sit in the grid's tree, so they bind to the Manager directly (WPF needed a `BindingProxy`). Columns aren't controls: the code reaches them by position (`Table.Columns[i]`). The WPF grid's traps (squeezed fixed columns, double-click auto-size, gripper hosts) have no twin here; dragging a divider was checked by hand in Phase 0.7.
  Widths aren't remembered; if they ever are, store star proportions.
- Status messages last 3 s (`StatusMessageDuration`), errors 6 s.
- **Resolved targets (#212).** `ScriptVariables.Resolve` fills a hand-written keycut's `SET` variables into its target for the Target column (`Keycut.ResolvedTarget`, `KeycutRowViewModel.DisplayTarget`), only when the target names a variable the script sets. It evaluates the lines before the launch line for the no-arguments case (args empty, `IF [NOT] "%~n"==""` decided on that); any other `IF`, `SET /A`/`/P`, delayed `!X!`, labels, `GOTO`, `CALL`, `FOR` leave variables unknown (`%NAME%`). Display only: `Keycut.Target`, Copy target, `CanEditInForm`, edits and writes use the file's text. Search matches both; sorting by Target uses what's shown. The tooltip lists the variables and the target as written. Fixtures in `tests/corpus/variables/` (outside `legacy`, so the characterization snapshots don't see them).

## Run counts (#187)

- keycuts isn't running when a keycut runs, so the `.bat` counts itself: `UsageLog.BatLines`, after the launch line and before `EXIT`, append one line to `%LOCALAPPDATA%\keycuts\usage\%~n0.runs`. Count = number of lines (`UsageLog.CountRuns`), last run = the file's write time. No `%DATE%` parsing, concurrent runs both count, and `%~n0` keeps counting under a name changed in Explorer.
- Both lines fail silently (the second is parenthesized so `2>NUL` covers the `>>` itself). The `.bat` keeps the launch's exit code: `ECHO` and a failed redirection leave ERRORLEVEL alone, and when the folder is missing, `MD` is followed by `"%ComSpec%" /C EXIT %ERRORLEVEL%` (expanded before `MD` runs) to put the code back. `UsageTests` runs the lines through real `cmd` with `LOCALAPPDATA` pointed at a temp folder. Cost (#240, Console Host, `ShellExecuteEx`): ~3 ms more console on screen (72 → 75 ms median), inside the noise; the first run, with the folder missing, ~30 ms once.
- No seeding from Windows' own launch history (#239): UserAssist is off for anyone who turned off app-launch tracking, recorded nothing in tests even with it on and Explorer restarted (not even an `.exe`), is undocumented, and misses terminal runs. The `.bat` lines are the only source.
- Parser: neither line is a launch line. `CanEditInForm` drops exact `BatLines` from both sides, so files with and without them stay editable; saving the form adds them.
- Older keycuts: `KeycutRepository.AddRunCounting` inserts the lines before a final `EXIT`, byte for byte (Latin-1 round trip keeps BOM, ANSI bytes, line breaks), restores the last write time, and skips anything else (no final `EXIT`, unparseable, read-only). The GUI runs it once per folder (`AddRunCountingOnce`), at startup and when Settings commits a new folder (`ShellViewModel.PrepareOutputFolder`, before the reload, #238). Every folder done is in `RunCountingFolders` (`REG_MULTI_SZ` in HKCU; the older single `RunCountingFolder` still counts as done), so lines removed by hand stay removed, even after switching away and back.
- `Keycut.Runs`: null = no record (file lacks the lines), 0 = counts but never ran. Only repositories built with a `UsageLog` read counts (`CreateDefault`); tests pass a temp one.
- Rename and the Edit form's rename move the record (replacing a leftover under the new name); delete removes it into `DeletedKeycut.Usage` and Undo restores it with its time. A brand-new keycut clears a leftover record for its name (`Runner.Usage`, set only by the CLI and `CreateOptions.Usage` from the GUI); overwriting keeps the count.
- Manager: Runs and Last run columns, sorted most/latest first. One column at a time: Modified makes way first (table < 1040), then Last run (< 780), then Runs (< 720); the table is the window less 48. Their headers' tooltip and help text say "Counting since <date>" (`CountingSinceText`, from `UsageLog.CountingSince`, the usage folder's creation time, read on each load; nothing before it exists), via `SortHeaderButton.Note` (#235).

## Migrating older keycuts (#196, #207)

- `KeycutMigration` in one pass: `REM <destination>` → `REM <target>`, and a launch line that is exactly `"%SystemRoot%\explorer.exe" "<one quoted argument>"` gets `START "" /B ` in front. Nothing else: not a commented-out copy, an unquoted argument or a second argument.
- Strict UTF-8 text with the file's own line breaks and BOM; a file that isn't valid UTF-8 is never rewritten (`NotUtf8`, doesn't block completion). Read-only, locked or changed-while-read files are `Skipped` and tried again next start.
- Every file that will change is copied to `<folder>\.keycuts-backup\<yyyyMMdd-HHmmss>\` (hidden, off PATH, never overwritten: `-2`, `-3`) before any is touched; if the backup fails nothing changes. Writes go through `ReplaceFileContent` (temp + `File.Replace`), and the last write and access times are put back.
- The GUI runs it once per folder (`RunOnce`, `MigratedFolders` in HKCU, added only when `IsComplete`): at startup next to `MoveAsideCommandNames`, before the first load, and on a folder change from Settings (`PrepareOutputFolder`). `MigrationNotice` says how many and where the backup is. The CLI never migrates. The Debug folder override runs it every start (idempotent).

## Target check (Missing / Warning / Unknown)

- Missing = a specific path was looked for and isn't there. Anything uncertain is Unknown (no label).
- `CheckTargetsAsync` checks `Keycut.Program` (or the target) with env vars expanded, records `CheckedPath`/`CheckedDetail` for the tooltip.
- A bare program name is looked up the way Windows does via `NameConflicts.Find`. For `START "" /D "<folder>" <program>`, see `CheckStartIn`: a program found by name needs the folder to exist; one only in App Paths works anyway (→ Warning).
- Text that can't be a path, or an extension not in PATHEXT, is Unknown.

## Name warnings

- `NameConflicts.Find` (pure; inputs via `NameConflictEnvironment`) lists what else a name opens from Win+R, in ShellExecuteEx order: Windows folder, System32, machine then user PATH, App Paths, each folder in full before the next. Before the output folder hides the keycut, after it is shadowed.
- Win+R ignores PATHEXT (#209, checked through the real Run dialog and ShellExecuteEx, which agree): it tries `.com`, `.exe`, `.bat`, `.lnk`, `.cmd` in that order (`RunDialogExtensions`), and never runs `.js`, `.vbs` or `.ps1` from a bare name. So `name.exe` beside a keycut hides it; `name.lnk`/`name.cmd` are shadowed. The target check passes `NameLookup.Cmd` instead, since a keycut's `START` runs under cmd, which does use PATHEXT.
- `NameCheck.Run` adds the existing keycut while "Ask before replacing" is on. GUI asks via `ConfirmWindow`; the CLI via `CreateConfirmation.Decide`, exiting 14 with redirected input.
- `AskBeforeReplacing` in HKCU; if unset, the old `ForceOverwrite` decides, inverted.
- `keycuts` and `keypaste` (`CommandNames`) are refused; `MoveAsideCommandNames` renames existing ones to `<name>_previous` at startup.

## Parser fallback

When REM type/target lines are missing or invalid, the launch line is tried in order: emitter's `cmd /C`, CLSID, folder, hosts, `START "" /D "<folder>" <program> [args]` (`TryReadStartInFolder`), file, command, URL.

- For the `/D` form, a quoted program with only quoted args joins into one path. Any unquoted program or argument gives `<folder>\<program>` as the target (not editable); the rest goes to `Arguments`/`Command` and the Target tooltip.
- Programs starting with `/`, unquoted ones containing `& | < > ^`, and cmd built-ins stay Commands.
- `Program`, `Arguments`, `StartInFolder`, `ProgramName` say where the program ends; they're empty for a quoted File target no pattern can split.
- `ShortcutFile.Unquote` removes exactly one pair of quotes; don't add another trim.
- The parser reads launch lines as written; it doesn't unescape.
- The hosts file is identified only by `Shortcut.IsHostsFile`.

## Update check

- `UpdateChecker` asks `GitHubReleaseSource` for `/releases/latest` at most once a day on GUI start. GitHub needs a `User-Agent`.
- Stored in HKCU: `LastUpdateCheck`, `DismissedRelease`, and `LatestReleaseSeen` as one `REG_MULTI_SZ` (version, URL), so one write is atomic. Anything but two non-empty lines counts as never checked.
- Compare three parts (`UpdateChecker.Normalize`); `Runner.Version` has four.
- A release URL that isn't an https page of this repo (`IsReleasePage`) becomes the releases page.

## Install, PATH, CLI

- PATH gets only the output folder (#248). The `keycuts.cmd` and `keypaste.cmd` shims (CRLF, `Common.CommandShims`, the same bytes as `keycuts.CLI/shims`, a test compares them) live there beside the keycuts, and run `keycuts.exe` from the install folder the MSI records in HKCU (`InstallFolder`), so their bytes are the same on every machine. The MSI installs them into `OUTPUTFOLDER`. `Runner.KeepCommandShims` (`CommandShims.Keep`) rewrites them in the keycuts folder at the GUI's start and wherever the folder changes (Settings through `ChangeOutputFolder`, the CLI's `-o` in `Run`), and deletes them from the folder they were last put in (`CommandShimFolder` in HKCU, stored with a trailing backslash) only if they are exactly the shims (`RemoveFrom`). Uninstall removes them from that recorded folder too (`SHIMFOLDER` and two `RemoveFile` rows). Only the installed copy does any of it, never under the Debug folder override. The shim clears `KEYCUTS_DIR` first, so an inherited one can't stand in for a missing `InstallFolder`. `keycuts.exe` can't go on PATH itself: a self-contained apphost needs its runtime beside it. Before #248 the install's `bin\` was on PATH; a major upgrade removes that entry with the old product.
- `OUTPUTFOLDER` is an MSI directory (trailing backslash, trimmed by `GetOutputFolder`); default from `[%USERPROFILE]`, matched to `Runner.DefaultOutputFolder` by a test.
- `UserPathUpdater` is a no-op when old and new folders match; the installer first adds the folder. Machine PATH entries are left alone.
- CLI help: `-h`/`--version` → stdout, exit 0; parse errors → stderr, exit 1. `paste` sets the clipboard via Win32 (no WinForms).
- `list` (#173's first verb, #237): loads through `KeycutRepository` with `UsageLog.CreateDefault()` like the GUI, and `KeycutListing` filters (name, type, target, description), sorts (the Manager's orders) and lines up the columns. `--usage` adds Runs and Last run (ISO local time); a dash is no record. Parser logging goes to stderr while loading, so stdout is only the table. An unreadable folder exits 3 (`CannotFindPath`). `--json` (`KeycutListing.ToJson`) always has name, type, target, description, runs, lastRun (null without a record) and file.
- `rm`, `rename`, `open` (#173) are `KeycutCommands` over `KeycutRepository.CreateDefault()`, so they follow the Manager: `rm` recycles and removes the run count; `rename` refuses taken or invalid names (exit 10 / 1), asks about a name another command has (`NameCheck`, as the Manager's rename does), `-f` skips it, and redirected input exits 14 (`ConfirmationNeeded`) like `create`; `open` starts the `.bat` through the shell with everything after the name, read before the option parser (`TryReadOpen`), so `-x` reaches the keycut (which ignores arguments until #172). The search is `KeycutListing.Matches`, the Manager's own rule. A name that isn't a keycut exits 2. The shims are never keycuts here.
- Windows 11 shows the verbs under "Show more options"; top-level needs a packaged `IExplorerCommand`.

## macOS: the script format

- `ShFormat` (an `IScriptFormat`, beside the `.bat` emitter `BatFormat`; `ScriptFormats.Current` picks one by platform). A keycut is `~/Shortcuts/<name>`: no extension, mode 755, UTF-8, LF. First line `#!/bin/sh`, second `# keycuts <version>` (that pair is what `IsKeycut` tests, so the Manager lists only keycuts: the `keycuts`/`keypaste` shims have a shebang but not the second line, and any other script in the folder is ignored, never deleted). Then `# <shortcut>…</shortcut>`, `# <type>`, `# <target>`, `# <description>`, the launch line, the run-counting lines, `exit $s`.
- Launch lines: Url, File and Folder are `open '<target>'`; a File with an app is `open -a '<app>' '<file>'`; a `.app` is a File (`open` launches it). Command is `/bin/sh -c '<command>'` (parsed; create never produces it, as on Windows). Single quotes, `'` written `'\''`. With "Use $HOME in paths" on, a target under the home folder is written `"$HOME/…"` (double quotes, `\ " $` and backtick escaped), and `PathVariables.ForMac` does the substitution after classification, as `Substitute` does on Windows.
- The run-count lines keep the launch's exit status (`s=$?` … `exit $s`), fail silently, and write `$HOME/Library/Application Support/keycuts/usage/${0##*/}.runs`: `${0##*/}` is the script's own name, so a rename in Finder keeps counting. Same model as the `.bat`'s (see Run counts).
- The header is read and rewritten by the same code as the `.bat`'s REM lines, with a comment prefix per format: rename rewrites only `<shortcut>`, a description edit only `<description>`, and `CanEditInForm` still allows only files the emitter re-writes identically. A file without the header is parsed from its launch line (`TryReadLaunchLine`: a target that isn't a path reads as a Url, a path as a File; a Folder needs the header).
- Running one (`MacDesktop.RunKeycutStart`): `/bin/sh <file> <args>`, the arguments split into words as sh would, nothing expanded, detached. It doesn't need the execute bit, so a script that lost its mode still runs from the Run box (Terminal needs the bit).
- Targets (`MacTargets`, plain file reads, tested everywhere): `~` is home; a symbolic link is followed to its final target, except a link into `/System/Cryptexes/` (`/Applications/Safari.app`), which keeps the path given (#290); a folder named `*.app` is a File; an XML `.webloc` is its URL (a binary one stays a File, which `open` opens); a Finder alias (bookmark data) is refused as Unsupported; no `{…}` is a CLSID. `.lnk`, `.url`, CLSID and hosts-file handling are Windows-only.
- Delete goes to the Trash (`TrashRecycler`, `trashItemAtURL`, so Finder's Put Back works) and returns where the file landed, which the Manager's Undo moves it back from. A volume with no Trash fails and the file stays.

## macOS: the Run box

- keycuts stays running with a template keycap in the menu bar (`MacMenuBar`: Run…, New keycut…, Manager, Settings…, Quit keycuts). Closing the window (red light, ⌘W, Escape) hides it and drops the Dock icon (`setActivationPolicy:` accessory); showing a screen brings both back; a Reopen activation shows the window. Explicit shutdown: only Quit ends the app.
- The shortcut is Carbon `RegisterEventHotKey` (`MacHotKey`; no Accessibility permission). It must include ⌘ or ⌃ (macOS 15 refuses otherwise; `RunBoxHotkey` enforces it). Default **⇧⌘Space** (⌃⌥Space and the others nearby are macOS's own). Stored as `Shift+Cmd+Space` in the `RunBoxHotkey` setting (unset is the default, empty is none), shown as `⇧⌘Space`. Settings' Run Box row records the next keys (the shortcut is paused meanwhile; Esc cancels, Delete clears); status `-9878` means another app has the combination and Settings says so.
- `RunBoxWindow` is borderless and topmost, a third of the way down the screen the mouse is on (`MacRunBox`). `RunBoxViewModel` shows up to `MaxRows` (6) rows from `RunBoxMatcher` (exact, then prefix, then contains in name, description or target; ties by runs, then last run, then name) or one "Create “name”…" row, which opens the Creator with the name filled. Return runs, Tab completes, Up/Down choose, Esc hides. The keycut runs through `Desktops.Current.RunKeycut` (detached, so its own lines count the run), then keycuts hides itself (`[NSApp hide:]`) so the previous app gets focus back, unless the main window is open.
- Open at login is `SMAppService.mainApp` (`MacLoginItem`, macOS 13+). A login start (#294) goes hidden in the menu bar. macOS gives no reliable signal for it (no launch Apple event in a normal start, launchd is every app's parent), so `LoginLaunch.Decide` takes a legacy login item's `lgit` event, or: registered, parent launchd and the user's login session under `LoginWindow` (3 minutes) old. A manual start in the first minutes after logging in therefore lands in the menu bar too; opening keycuts again shows the window. macOS lists the item switched off until approved in System Settings → General → Login Items; Settings says so (`NeedsApproval`).
- Windows has the same box and a tray (`WindowsHotKey`, `WindowsRunBox`, `WindowsTray`; default Ctrl+Alt+Space), over the same view models.

## macOS: the settings file

- `RegistryStuff` reads and writes through `ISettingsBackend`: the registry on Windows, `JsonSettingsBackend` on macOS, one JSON object in `~/Library/Application Support/keycuts/settings.json` (`Environment.SpecialFolder.LocalApplicationData` is that folder on macOS), with the registry's value names. A string is a JSON string, a DWORD a number, a multi-string an array of strings. Unknown values survive a write; a missing or unreadable file reads as empty; every write goes to a temp file and is moved over the old one. Tests use a temp path (`new JsonSettingsBackend(path)`), never `DefaultPath`.
- The same folder holds `install-folder` (one line, the folder the app runs from, written at the app's start; the `keycuts`/`keypaste` shims in the keycuts folder read it, so their bytes are the same on every Mac) and `usage/` (the `.runs` files). The keycuts folder itself, `~/Shortcuts`, is the `OutputFolder` setting; `KEYCUTS_OUTPUT_FOLDER` overrides it in Debug builds.
- `RightClickContextMenu` records the Quick Action choice; the toggle shows whether the workflow is really installed.

## macOS: the PATH block

- Only Terminal needs it; the Run box finds keycuts itself. It is opt-in: Settings' **Run keycuts in Terminal** or `keycuts path add`. `MacShellPath` writes a marked block at the end of `~/.zprofile` (zsh) or `~/.bash_profile` (bash), picked from `$SHELL`: a blank line, `# >>> keycuts >>>`, one `export PATH="<folder>:$PATH"` (a folder under home as `$HOME/…`, inside double quotes, so `\ " $` and backtick are escaped), `# <<< keycuts <<<`. Other shells (fish, nu) get `Instructions` to copy instead; Settings disables the switch.
- `Remove` takes out exactly that block, so the rest of the profile is byte-identical. The file is written in place, so a symlinked dotfile stays a symlink. A folder that holds `:` or a line break can't be on PATH and is refused.
- `Status`: **OnPath** when the folder is on this process's PATH or in `/etc/paths` (or `/etc/paths.d`), **InProfile** when the block names it but this shell started before it ("open a new Terminal window"), else **NotOnPath**. Something other than keycuts having put the folder on PATH disables the switch.
- A folder change (Settings, `-o`) moves an existing block to the new folder (`AddToOrReplace`) and, with no block, adds nothing: PATH was never agreed to. `UserPathUpdater` (the registry) is the Windows twin and GUI creates never change PATH on either. Tests pass a temp home and PATH.

## macOS: the Quick Action

- `installer/macos/keycut this!.workflow` is an Automator Quick Action for Finder: a Run Shell Script that runs `open -b com.teamralon.keycuts "$@"` on the selected items (paths arrive as arguments, spaces included). `QuickActionInstaller` copies it to `~/Library/Services` and runs `pbs -flush`; the source is `BundleResources.Folder("QuickAction")`.
- The app installs it at its own start (`RegistryStuff.EnsureQuickAction`, unless Settings turned it off) and replaces an older copy when the files differ (`IsUpToDate`); there is no package postinstall (#106). Settings' toggle and `keycuts install-shell-integration` / `uninstall-shell-integration` install and remove it, and the toggle shows whether it is installed.
- The running app receives the files (`MacFileOpen`: `FileActivatedEventArgs`, from the Quick Action, a drop on the Dock icon or `open -a`) and fills the Creator with the first one. `Info.plist.in` declares `public.item` and `public.folder` with `LSHandlerRank` None, so keycuts is a target for them without becoming a default in Open With.
- macOS lists a new service switched off: the item is missing from Finder's right-click until it is turned on in System Settings → General → Login Items & Extensions → Extensions → Finder. The app can't do that for the user; the README and Settings say so. There is no item for a folder's background, which Windows has.

## macOS: the app bundle and the release

- **Bundle data lives in `Contents/Resources`, never in `Contents/MacOS`.** The bundle's signature treats every file in `Contents/MacOS` as code to seal, and Apple's notary refused the first submission ("the signature of the binary is invalid" on `keycuts.GUI`) because `QuickAction`, `icons` and `shims` sat there; the same app without them was accepted. `tools/Build-MacPackage.sh` moves `QuickAction` and `icons` to `Contents/Resources` and deletes the Windows `.cmd` shims. Code reads them through `BundleResources.Folder(name)`, which prefers `../Resources/<name>` from the executable and falls back to the folder beside it (dev builds and `tools/mac/new-*-bundle.sh`). Anything new the app ships as data goes through it.
- The bundle: `keycuts.GUI` (the app) and `keycuts` (the CLI) side by side in `Contents/MacOS`, `Info.plist` from `installer/macos/Info.plist.in` (`com.teamralon.keycuts`, macOS 13+), `keycuts.icns` from `tools/mac/make-icns.sh` (Porcelain, fixed: it is the Dock icon too, running or pinned, and macOS Settings offers no icon choice, #314). Signing is inside-out: every file in `Contents/MacOS`, then the bundle (hardened runtime and `entitlements.plist` with a real identity; ad-hoc without one, which still has to sign each nested file), then `pkgbuild`, `productbuild`, `productsign`, `notarytool`, `stapler`.
- `release.yml` has five jobs: `version` (reads `<Version>`, decides whether to build and publish), `windows` (tests, MSIs, zips) and `macos` (both `.pkg` files, signed and notarized) in parallel, `publish` (checks the files, writes `SHA256SUMS.txt` over all of them, makes the release as a draft and publishes it once every file is attached) and `cask` (opens the Homebrew cask PR in `andrewralon/homebrew-tap` with `tools/mac/update-cask.sh`; its own job, so a failure leaves the release alone). Nothing is public until both builds pass. `gh workflow run release.yml --ref <branch> -f dry_run=true` tries everything but the release and the cask PR and keeps the files as artifacts. The cask token (`HOMEBREW_TAP_TOKEN`) expires: rotate it, or the cask PR quietly stops.
